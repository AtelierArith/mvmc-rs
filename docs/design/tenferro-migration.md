# tenferro migration (v0.8 to v0.9)

The root and standalone CUDA workspaces use the caller-owned tenferro Engine API. The root workspace selects the `native` CPU provider and remains independent of CUDA. The benchmark and CUDA workspaces maintain separate lockfiles; the locks are authoritative for each dependency graph.

## v0.9 (issue #644)

The root workspace, the standalone CUDA workspace (`gpu/mvmc-gpu-cuda`, `gpu/tenferro-ext`) and the standalone `benchmark/pfapack_compare` lock resolve tenferro 0.9.0 (all components, including tenferro-cpu), threadteam 0.3.0, strided-basic/-perm/-kernel/-fused/-nn 0.10.0, t4a-faer 0.28.2, tcontract 0.9.1, cpueinsum 0.9.1 and tlinalg 0.8.1. mvmc-rs passes no `threadteam`, `faer` or `strided` type across a tenferro boundary, and it never used the retired graph AD emitter (`tenferro_ops::ad::linearize`, `transpose_rule`, `transpose_input`), so the bump needed no source migration for those changes.

`CpuEngine::with_exec` replaces the bare `CpuEngine::exec` bundle in the experimental shared-team probe dispatcher (`MVMC_EXPERIMENT_SHARED_CPU_TEAM=1`, `stage_backend::try_probe_cpu_blocks`). The blocks now run as an Engine operation: a panic marks the Engine broken, and a broken Engine refuses the call without running any block. The caller then runs the fixed blocks serially, as it did before when it could not get the execution bundle. `with_exec` lends an existing Engine's team to downstream work; it does not limit how many workers independent Engines create. The `MVMC_RS_TENFERRO_THREADS` per-Engine bound (#589) and the `MVMC_RS_TENFERRO_WORKER_BUDGET` process-local reservation (#616) therefore remain. They are not workarounds for a missing tenferro entry point.

CPU C-order outputs and RNG are unchanged. Of the tenferro SR checks, only the CG local product changed, at roundoff level, because faer's GEMM backend moved from `gemm` 0.19 to `t4a-gemm` 0.20; every existing bound passes unchanged. The SR stage timings before and after are in [benchmark/tenferro_cpu_v09/README.md](../../benchmark/tenferro_cpu_v09/README.md).

The `third_party/tenferro-{ad,cpu,einsum,runtime,gpu}` 0.7.1 lru snapshots (#192/#420) were deleted together with their workspace `exclude` entries. No lock resolves them, and every lock resolves `lru 0.18.5`; see `docs/security/dependabot-alert-5.md`.

The v0.8 migration history follows. Its implementation is #588, with singular/collective fixes and numerical evidence in #589/#592/#594, dependency remediation in #596, and the final ownership evaluation in #620–#622.

## CPU ownership

The SR and measurement stages in one `StageBackend` share an eager context and a mutex-protected caller-owned Engine. The engine is borrowed exclusively for a complete operation or transfer. CPU construction uses `MVMC_RS_TENFERRO_THREADS` if set, otherwise `RAYON_NUM_THREADS`, falling back to the process's available parallelism when both are absent; one thread selects a serial Engine and larger values create a `threadteam` pool. The mVMC Rayon pool and the tenferro pool are separate, so callers running multiple walkers must still control their combined thread budget. Parallel utilization, nested pool behavior, and wait policies need measured validation; the existence of multiple threads does not establish a speedup.

The normal non-C-order stage acquisition uses one process-wide shared stage, so concurrent acquisitions serialize on its mutex. Direct construction of multiple `StageBackend::tenferro_cpu()` instances can create independent pools. MPI processes also have independent pools. `RAYON_NUM_THREADS` is therefore not a global limit on all runnable threads: a Rayon worker, a tenferro team, other walkers and BLAS threads may overlap. Use `MVMC_RS_TENFERRO_THREADS=1` and `OPENBLAS_NUM_THREADS=1` where a single-threaded tenferro stage is required without changing other Rayon users.

The [ownership evaluation and policy](../../benchmark/tenferro_thread_budget/ownership-evaluation-20261102/README.md) supplies the explicit combined accounting and measured selection rules. `MVMC_RS_TENFERRO_WORKER_BUDGET` bounds process-local additional Engine reservations, including independent factories and scoped team replacement; the Engine is destroyed before its reservation returns. A reservation failure selects a serial Engine without waiting. `MVMC_RS_MPI_CPUS_PER_RANK` plans disjoint node-local masks, checks the inner-plus-additional-worker budget and updates both the caller and existing inner workers, with collective rollback/recovery. Callers still supply quota/BLAS/external-pool accounting; there is no automatic global scheduler. A solve lease retains the team across SR-CG products without holding the stage mutex over collectives. Static subtraction caps and per-product recreation were rejected for measured regressions. The evaluated shared-team path remains opt-in; Rayon/default work gates are retained.

An idle-only probe on the migration host, sampled three seconds after stage creation, observed one OS thread and 0.0% CPU with `RAYON_NUM_THREADS=1`, and five OS threads and 0.3% CPU with `RAYON_NUM_THREADS=4`. The ten-second `crates/mvmc-core/examples/tenferro_idle_probe.rs` program reproduces that observation when inspected with `ps`. This single idle sample does not measure active worker overlap, nesting, affinity, MPI or performance.

## CUDA ownership

Each CUDA Engine owns a runtime and stream. The eager context and its Engine are explicitly paired; uploads, eager operations and downloads borrow that same Engine. A raw-execution scope visits the actual CUDA Engine and uses its stream. Downstream specialized kernels are compiled by NVRTC and loaded by the CUDA driver because tenferro's raw session (still in 0.9) exposes no downstream kernel compilation or launch surface. Compilation flags are part of the module cache key; the standalone Pfaffian kernel disables fused multiply-add as before.

Raw device buffers are retained on the CUDA primary context, associated with their originating runtime identity, and rejected by other runtimes even on the same device. Device buffers, loaded modules, pinned staging and native handles must remain live until their stream work completes. Raw scopes synchronize on both successful and returned-error paths; this does not by itself establish panic safety or remove the caller's responsibility for asynchronous buffer lifetimes. Keep transfer and synchronization counts visible in validation. No cross-device pointer borrowing or silent CPU fallback is permitted.

The production Pfaffian stage owns its persistent CUDA worker instead of leaking it. Dropping the stage closes the work channel and joins the worker. This changes resource lifetime; GPU tests must exercise repeated creation, use and destruction before merge.

## Numerical and security boundaries

CPU C-order execution retains the C numerical and SFMT contract. The resident GPU Opt path has a separate Julia GPU numerical and RNG contract; passing one path's tests does not validate the other. Review singular solve behavior and reduction-order changes when validating each tenferro update. Preserve explicit tolerances, first-divergence evidence and independent RNG checks.

The migration checks compare real and complex CPU Gram products to the C-order path under explicit dot-product bounds, and verify Cholesky solutions with residual bounds (`sr_backend_421`). The same gate rejects a non-positive-definite matrix and exact singular zero/rank-one matrices for both C-order and the CPU Engine; CUDA's resident SR gate also exercises non-positive-definite and singular zero-Gram solves and subsequent reuse. These are tested cases, not a claim that every ill-conditioned or provider-specific failure mode is classified. The 1- and 4-thread CPU SR timings and observed differences are in `benchmark/tenferro_cpu_v08/README.md`; different legal contraction/reduction orders need not be bitwise identical. Four-rank Opt/PhysCal formatted-output comparisons and their RNG limitations are recorded in `benchmark/tenferro_thread_budget/multi-process.md`.

The tenferro 0.7.1 `lru` patch snapshots were removed in #644. Verify each dependency tree; the historical provenance is retained in `docs/security/dependabot-alert-5.md`.

## Shared Pfaffian extension

The production measurement selector `MVMC_RS_MEASURE_PF_BACKEND=tenferro` remains unsupported and is rejected before I/O, collectively under MPI. This limitation predates the migration: `stage_backend.rs` at CPU migration baseline `af6aa25c68e821e4771b9db16580a4706787941a` already uses `UnsupportedPfaffian` for tenferro 0.7.1. The default C-order measurement and the standalone shared extension below are separate working contracts. Wiring a supported production selector is the explicit follow-up #613, not a claim that the existing extension is absent or a lost 0.7 production path.

`mvmc_gpu::tenferro_ext::PfaffianInverseOp` defines a multi-output tenferro operation on compact column-major `[n,n,NQP,B]` tensors. It accepts real `f64` and `Complex64`; matrix side `n` must be even and at least 2. It returns Pfaffians `[NQP,B]`, true inverses `[n,n,NQP,B]` (the mVMC stored `invM` is their negation), and i32 per-plane status `[NQP,B]`: zero for success, a positive one-based zero-pivot row, and `-1` for a non-finite Pfaffian. Failed inverse planes are zero-filled. Neither provider silently falls back to another device.

Register `cpu_extension_module` with a caller-held CPU Engine, using the matching tenferro Engine ID. Use `TraceContext::add_extension` and `GraphCompiler::compile_traced_graph` to produce a reusable multi-output program. The CUDA provider `mvmc_gpu_cuda::pfaffian_extension::cuda_extension_module` and its gate had no production consumer and were removed in #643; the paragraph below records the contract it had.

The CUDA executor accepts owned, compact tensors in the same allocation domain and supports `n <= 1024`; it explicitly rejects tensor views and unsupported shapes or scalar types. Empty batches are accepted. It keeps input and outputs on that engine, runs the specialized CUDA kernel, and retains at most 64 MiB of intermediate scratch through the engine's bounded extension cache. Larger scratch allocations are scoped to the call. The compiled module is stored in the same engine-owned cache, with its host PTX length used as the retained-byte estimate; this is not a measurement of driver-side module memory. When the cache cannot retain the module, the executor synchronizes before releasing it. The executor synchronizes its raw scope before returning; it does not claim asynchronous behavior. Existing production sampler kernels remain unchanged and are not automatically replaced by this API.
