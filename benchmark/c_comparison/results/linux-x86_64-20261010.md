# Native C versus Rust: Linux x86_64, 2026-10-10

Historical pre-fix measurements. Follow-up #492 found that `opt_heisenberg_fsz`
auto-loaded `initial.def` only on Rust; its timing is not an input-matched
comparison. The RBM OptTrans case also used different SR derivative/selection
semantics. Those two rows must not support equivalent-work speed claims.
The maintained `scripts/bench_native_c.py` disables Rust's automatic initial
file and the #492 report records corrected behavior and numerical evidence.

At one computation thread, Rust is faster on all 13 measured workloads: 1.14–3.46x by the internal timer. At four configured computation threads, C is faster on Hubbard optimization L32 (1.56x), L64 (1.14x), and PhysCal L32 (1.35x). L16 optimization differs by only 6% in Rust's favor. Performance depends on workload and threading.

AMD Ryzen 9 PRO 8945HS; both programs executed in the same Dev Container. One discarded warm-up and three measured repetitions per implementation and workload. Values below are medians in seconds. `C/Rust > 1` means Rust is faster.

The primary time is internal timer `[0] All`, including initialization and calculation, excluding MPI startup outside the timer. Wall time includes launch and shutdown; only C uses `mpirun -np 1`. See [measurement setup and reproduction](../README.md), [environment](environment-20261010.txt) and [input hashes/overrides](inputs-20261010.json).

## Scope and limits

These are input-matched executable benchmarks, not standalone Pfaffian kernel benchmarks or a new deterministic reference-parity audit. Rust source is commit `72ca4e99` plus the user changes listed in the environment file; C submodule is `d73d06bd529d3b2573f38eb5817c4a5f52971006`, copied and built without patches. Release compilation and C build time are excluded. C uses upstream default GEMMT support with downloaded BLIS; blocked Pfaffian updates are disabled. Rust uses its default enabled OpenBLAS backend, without enabling the optional SIMD feature.

The workload overrides and parameter files match on both sides. Optimization timing covers fixed step counts; PhysCal covers fixed sample/data counts. Timing does not prove identical accepted moves or RNG trajectories. No statistical averaging is used to claim numerical agreement, and no numerical tolerances or reference fixtures were changed.

Thread counts describe configured workers, not measured utilization: Rust runtime gates can keep small kernels serial. The 4-thread table therefore compares default application behavior at that configuration, rather than asserting four active workers in every kernel. C OpenMP overhead can likewise dominate small problems. CPU frequency and shared-machine load were not controlled; each implementation ran sequentially, and per-run load is in the CSV. Differences of a few percent should not be treated as conclusive.

No benchmark-driven implementation changes were made. The repository-wide test suite was not rerun for this read/build/measurement task.
