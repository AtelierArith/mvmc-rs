# Main C / Julia / Rust MPI layout sweep

This repeats the complete six-layout experiment after the Julia partial-pool
QP dispatch and Rust bounded measurement-team changes were merged. The 1×1
configuration is the baseline; 1×16, 2×8, 4×4, 8×2 and 16×1 exhaust the positive
integer rank/thread combinations whose product is 16.

Source checkout: `0f86e42e3881c68b97cad9fb5a2979f7959de89d`, with no tracked
changes. C: `d73d06bd529d3b2573f38eb5817c4a5f52971006`; Julia:
`62416e30a04e33a6d3641351fa8487dd640473cb` (upstream PR #78 merged).
Related to #496. The earlier sweep in PR #512 is a separate experiment.

Periodic half-filled one-dimensional Hubbard chain, t=1 and U=4, 32/64 sites.
Opt runs 300 SR steps; PhysCal runs 100 groups. Each step/group has **320 total
saved samples**, divided evenly over ranks; this differs from the earlier
300-sample 4×4 report. Each cell uses one warmup and three measured repetitions.
Tables report medians in seconds. BLAS uses one thread.

Measurements run sequentially on Linux x86_64, AMD Ryzen 9 PRO 8945HS (8 physical
cores, 16 logical CPUs), in the 1 GiB shared-memory Dev Container
`mvmc-rust-issue496-shm1g`. Julia 1.13.1 uses the pinned benchmark lock;
MPI is MPICH 4.2.0. Compiler versions and actual BLAS providers are retained in
each configuration's logs. Cargo release builds enable `mpi` and use a separate
checkout target directory, without extra Rust compiler flags.

C uses its rank-zero internal All timer after MPI_Init. Julia and Rust use the
maximum rank time of their warmed production APIs. Startup, JIT, build and
warmup are excluded, but these timing boundaries differ. Within each
size/layout, PhysCal uses the same parameter file generated by the first
measured C optimization. Different layouts have different RNG trajectories
and parameter files: this measures end-to-end workloads, not fixed-trajectory
strong scaling. Output shape and finite-value validation do not establish
cross-language numerical or RNG parity.

Run `bash run.sh NEW_OUTPUT_DIRECTORY` from this directory in the Linux Dev
Container, with a repository checkout at the source above. The script invokes
`bash bench/run.sh` for all six layouts. Build Julia's SFMT/PfaPack native helpers
in the canonical reference project first as described in the development
documentation. The output directory must be new.

`report.md` contains all six requested C/Julia/Rust tables. `measurements.json`
contains the complete 216 measured times. Each layout preserves input files,
source/binary hashes, timing records, compressed execution logs and measured
optimization/observable outputs. `summarize.py` verifies the complete cell and
repetition coverage and regenerates the table from the raw measurements.

Validation passed for all 216 positive finite timings, 2,302 unchanged source /
binary hashes per layout, and all raw optimization / physical-output shapes and
finite values. `validate-raw.py` records that developer check and requires the
original raw output tree. `verify.py` checks the exported checksums, clean source
provenance and all 10,908 measured output files without reference runtimes.
Run both `uv run --no-project python summarize.py` and
`uv run --no-project python verify.py` from this directory.

Opt medians are smallest at 8×2 for all three implementations at both sizes.
PhysCal's fastest layout depends on implementation and size: C and Rust prefer
16×1 at 32 sites and 8×2 at 64 sites; Julia prefers 8×2 at both sizes. Small
differences between neighboring layouts are not evidence of stable superiority.
Julia 1×16 at 64 sites is faster than its 1×1 baseline for both workloads, while
the 32-site medians remain close. No universal speedup from increasing thread
count is claimed.
